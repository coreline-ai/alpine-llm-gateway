# Gateway 자동 복구 Stop 경쟁 조건 보강 계획

작성일: 2026-08-09
범위: `alpine-llm-bridge` recovery supervisor와 `integrated-app` Gateway lifecycle 연결

## 배경

기존 Gateway lifecycle은 health 확인, 최대 2회 자동 복구, 명시적 Stop 시 monitoring generation
폐기를 이미 제공한다. 그러나 health failure가 이미 restart callback을 시작한 직후 사용자가
`종료`를 누르는 경쟁 상황에서는 callback 내부가 Stop 의도를 직접 확인할 수 없었다. 이 작업은
chat prompt·terminal command를 재실행하지 않는 기존 계약을 바꾸지 않고, recovery callback에
세대 기반 취소 lease를 전달해 Stop/owner 변경 뒤 자동 restart의 최종 상태가 남지 않도록 보강한다.

## 범위 밖

- 실제 Provider 계정 OAuth/API 호출, prompt replay, provider 자동 fallback
- PRoot terminal resize, Doze/reboot/process-kill, x86_64 emulator E2E
- 실 Gateway process를 고의 crash시키는 production-like Samsung fault injection

## Phase 1. 경쟁 조건 계약과 테스트

- [x] recovery restart callback에 현재 monitoring generation만 유효한지 확인할 수 있는 read-only lease를 추가했다.
- [x] explicit Stop 이후 이미 시작된 restart callback이 lease를 revoked로 보는 단위 회귀를 추가했다.
- [x] lease가 취소된 callback은 추가 health/restart scheduling을 만들지 않는지 확인했다.

## Phase 2. 통합 Host 적용

- [x] `IntegratedAlpineLlmHost` 자동 복구가 restart 전·후 lease와 현재 controller owner를 확인하도록 했다.
- [x] Stop, provider/model owner swap, close 뒤에는 stale recovery가 Runtime binding이나 새 owner를 건드리지 않도록 했다.
- [x] recovery 취소는 이전 prompt·terminal command·direct Provider fallback을 절대 실행하지 않는 계약을 유지한다.

## Phase 3. 검증·문서

- [x] Bridge unit test와 integrated APK/lint를 실행했다.
- [x] 가능한 정적 boundary 회귀 및 Python suite를 실행했다.
- [x] README, runtime integration guide, master plan을 실제 보장 범위로 동기화했고 `release-readiness.json`은 외부 gate 상태가 변하지 않아 `release_ready=false`를 유지했다.
- [x] `git diff --check`를 통과했다.

## 완료 조건

- 사용자의 명시적 Stop/owner 변경은 recovery lease를 즉시 revoke한다.
- 이미 queued된 recovery는 restart 전 취소되고, restart 도중 취소되면 owner가 다시 안정 Stop 상태가 된다.
- 자동 복구는 Gateway/Runtime lifecycle만 다루며 prompt/command/provider dispatch를 재실행하지 않는다.
- 외부 실계정·OEM lifecycle 검증은 완료로 표기하지 않고 `NOT_RUN`/`BLOCKED`로 유지한다.
