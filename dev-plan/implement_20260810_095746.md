## 개발 목적

- 한 Provider profile에 여러 모델 후보를 안전하게 보관하고, 채팅에서 선택할 수 있게 한다.
- 기존 단일 `ProviderProfile.model` 저장값을 손실 없이 카탈로그의 기본 모델로 승격한다.
- Provider가 승인한 정적 목록(Gemini)과 사용자가 직접 등록한 모델을 UI·저장·세션 생성에서 같은 방식으로 다룬다.
- 목록에서 제외된 모델을 과거 대화에서 자동으로 다른 모델로 바꾸지 않고, 사용자에게 명시적 재선택을 요구한다.

## 문서 기반 제약 사항

- OAuth token, authorization code, PKCE state/verifier, Provider raw response·URL·headers·prompt는 모델 카탈로그, UI state, log, test fixture에 넣지 않는다.
- 모델 후보는 계정·region·tier·preview lifecycle의 지원 증거가 아니다. 실계정 E2E 전에는 non-Gemini 후보를 `USER_ADDED`로만 취급한다.
- 채팅 생성은 사용자가 누른 Retry만 새 요청으로 보며, 후보 전환·목록 변경을 이유로 자동 dispatch/replay하지 않는다.
- current `ProviderProfileStore`는 profile 전체를 하나의 JSON 배열로 원자 저장한다. 이번 범위에서는 별도 catalog store를 만들지 않고 profile-owned schema로 확장해 profile/catalog 불일치와 다중 store migration을 피한다.
- 현재 `ChatBackendDescriptor.modelOptions`, `ChatViewModel.selectModel`, `DirectChatHostController.session(profileId, model)`은 다중 모델을 이미 지원한다. 모델 그룹이나 새 routing 계층을 만들지 않는다.

## 확인·결정 기록

- 결정: 후보의 식별자는 Provider로 보내는 `modelId` 문자열이다. 별도 UUID·표시명 override·capability metadata는 현 채팅 계약에 필요하지 않아 추가하지 않는다.
- 결정: 후보 source는 `PROVIDER_APPROVED`, `USER_ADDED`, `LEGACY_MIGRATED`로 제한한다. 동적 discovery source와 네트워크 refresh는 후속 별도 계획에서만 추가한다.
- 결정: 후보 삭제 대신 `enabled` 전환을 사용한다. 과거 대화가 참조한 model ID를 보존하며, disabled 후보는 새 선택·발송 대상에서 제외한다.
- 결정: profile의 기존 `model` 필드는 기본 선택 모델로 유지한다. 새 JSON key가 없는 이전 profile은 해당 값으로 `LEGACY_MIGRATED` 후보 하나를 생성한다.
- 결정: Gemini만 `GeminiProfileDefaults.MODELS`를 `PROVIDER_APPROVED` 후보로 seed한다. 다른 Provider에 추측성·OpenMinis 유래 기본 목록을 추가하지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고, 각 단위의 역할과 경계를 계획에 적는다.
- 모델 후보 값은 normalize한 non-blank model ID만 보관하고, 중복은 대소문자 구분 없이 한 항목으로 합친다. Provider에 전송하는 원문 ID는 최초 등록 값을 유지한다.
- OAuth identity 값 변경과 모델 카탈로그 변경을 분리한다. 후보·기본 모델 변경은 token 삭제나 재로그인을 유발하지 않는다.
- raw Provider 모델 목록은 수집하지 않는다. 테스트는 fake session과 정적 fixture만 사용한다.
- 구현 후 OpenMinis 문자열·CLI fingerprint·consumer identity가 production source/APK에 추가되지 않았음을 release verifier로 확인한다.

## 잔여 리스크 / 후속 과제

- Provider가 앱 소유 OAuth registration에 대해 model discovery를 공식 지원하고, endpoint·scope·권한·response shape를 문서화한 뒤에만 별도 계획으로 `DISCOVERED` 후보와 refresh를 검토한다.
- 그 후속 계획은 account/region/tier mismatch, preview retire, stale cache, 401/403, discovery rate limit, raw response redaction을 별도 E2E gate로 다뤄야 한다.
- 실제 Codex OAuth/inference 성공 여부와 OpenMinis 호환 debug profile의 유지·격리·폐기는 이 계획 범위 밖이며, 공개 배포 `NO-GO` 상태를 변경하지 않는다.
