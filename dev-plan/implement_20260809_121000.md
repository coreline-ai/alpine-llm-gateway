# APK mutation simulation preflight 계획

작성 일시: `2026-08-09 12:10:00 KST`

## 목적

Package UI는 allowlist·사용자 승인·fixed argv를 이미 적용한다. 그러나 승인 뒤 첫 command가 곧바로
mutation이어서 cached repository가 즉시 거부할 request를 Runtime 변경 없이 구분할 수 없다.
`apk --simulate`를 **승인 뒤·mutation 전**에 고정 argv로 실행하고 실패하면 실제 `apk add/del/upgrade`를
보내지 않는 fail-closed preflight를 추가한다.

Alpine 공식 문서의 `--simulate` 계약은 mutation 없이 요청을 simulation하지만 missing/stale index에는
신뢰할 수 없다고 명시한다. 따라서 이 작업은 live repository freshness, network, dependency total,
filesystem 여유, cancellation 또는 disk-full E2E를 완료로 표기하지 않는다.

## 범위

- `RuntimePackageInstaller`와 `RuntimePackageMutator`가 policy 및 explicit approval 뒤
  `apk <subcommand> --simulate --no-progress <validated names>`를 실행한다.
- simulation이 non-zero·timeout·transport exception이면 stable `PREFLIGHT_FAILED` 결과를 반환하고 mutation argv를
  절대 dispatch하지 않는다.
- UI는 raw APK output 없이 simulation 실패와 Runtime 미변경 상태를 표시한다.
- API, Host, Compose 회귀와 Samsung product APK rebuild/cold start를 검증한다.

## 제외 범위

- `apk update`/live repository lookup, stale-index freshness 보장, 실제 network·cancel·disk-full 테스트
- package metadata를 authorization source로 사용하는 변경
- rootfs/PRoot resize, Provider 계정, Doze/reboot, x86_64 emulator 및 공개 배포 gate

## 안전 조건

- policy와 user approval 이전에는 simulation도 실행하지 않는다.
- input은 기존 validated exact package names만 재사용하며 shell/environment/user text를 받지 않는다.
- preflight와 mutation output은 Host/Compose state·문서에 저장하지 않는다.
- actual mutation은 only-after-simulation-success이며 automatic retry/fallback을 추가하지 않는다.

## 구현 결과

- `RuntimePackageInstaller`와 `RuntimePackageMutator`는 `apk add|del|upgrade --simulate --no-progress`
  를 실제 변경 직전에 고정 argv로 실행한다. simulation의 non-zero·timeout·exception은 모두
  `PREFLIGHT_FAILED`로 귀결되고, 후속 mutation은 dispatch하지 않는다.
- install non-zero, remove timeout, install transport exception 회귀 테스트가 첫 simulation request만
  기록하고 `PREFLIGHT_FAILED`를 반환하는 것을 검증한다. 정상 add/update는 simulation 성공 뒤에만
  실제 command를 보낸다.
- Compose는 `사전 확인 실패`와 Runtime 미변경 안내만 노출하며 APK 원문 출력을 표시하지 않는다.
