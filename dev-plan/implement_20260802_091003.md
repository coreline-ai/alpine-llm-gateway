# implement_20260802_091003.md

작성 일시: `2026-08-02 09:10:03 KST`

문서 상태: **로컬 구현·검증 완료 / 외부 E2E·공개 배포 차단 유지**

이 문서는 P1·P2 구현 이후 남은 기술·실기기·실계정·스토어·공개 배포 gate의 범위를 고정하고, 외부 조건이 없는 상태를 성공으로 기록하지 않기 위한 작업 문서다.

## 개발 목적

- 현재 fail-closed 상태로 남겨 둔 동적 terminal resize와 실험 x86_64 지원을 검증 가능한 수준으로 마무리한다.
- 실제 Provider 계정, Play Asset Delivery, 재부팅·Doze 환경에서 제품 수준 E2E를 수행한다.
- Gradle 9 비호환 경고를 제거하고 전체 SDK·외부 consumer matrix를 새 빌드 기준으로 검증한다.
- 프로젝트 라이선스, complete corresponding source, 서명·배포 책임과 원격 CI를 확정해 공개 배포 가능 여부를 판단한다.
- 외부 조건이 충족되지 않은 항목은 `BLOCKED` 또는 `NOT_RUN`으로 남기며 거짓 완료하지 않는다.

## 개발 범위

- P1: PRoot guest 동적 terminal resize 설계·구현·Samsung 실기기 검증.
- P1: 실제 Provider 계정 OAuth/API 모델 조회, non-stream, stream, cancel, logout E2E.
- P1: signed AAB와 Play test track을 이용한 Asset Delivery 설치·업데이트·복구 E2E.
- P1: Samsung 재부팅, process kill, Doze, 배터리 제한과 Foreground Service 복구 검증.
- P1: 프로젝트 라이선스·PRoot/talloc 대응 소스·서명 key owner·원격 배포 위치 확정.
- P1: GitHub 원격 CI, release bundle, publication/consumer matrix 전체 통합 검증.
- P2: x86_64 API 35+ emulator runtime E2E와 지원 승격 판단.
- P2: Gradle 9/호환 AGP 전환, deprecated feature 제거와 회귀 검증.
- 문서, release manifest와 검증 보고서의 실제 결과 반영.

## 제외 범위

- 저장소 소유자 승인 없이 프로젝트 라이선스를 임의로 선택하는 작업.
- production signing key를 새로 만들거나 저장소·CI 로그에 key/비밀번호를 기록하는 작업.
- 사용자 승인 없이 Provider 실계정을 호출하거나 비용을 발생시키는 작업.
- 다른 앱의 public client ID, OAuth token, cookie, API key를 복사·추출하는 작업.
- 실제 Provider에 의도적으로 429·5xx를 발생시키는 작업. 해당 오류는 fake Provider 회귀 테스트로 유지한다.
- 사용자 승인 없이 실기기를 재부팅하거나 Doze/강제 종료를 수행하는 작업.
- E2E를 통과하지 않은 x86_64, 동적 resize 또는 Play 공급 경로를 제품 지원으로 표시하는 작업.
- Alpine 작업 모드와 무관한 채팅 UI, Provider 기능 또는 범용 파일 관리자 확장.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 외부 계정·기기·스토어·법률 결정이 없으면 성공으로 간주하지 않고 차단 이유와 owner를 기록한다.
- 실계정·실기기 보고서에는 token, cookie, API key, raw request/response, 사용자 prompt를 저장하지 않는다.
- 새로운 capability는 성공 경로뿐 아니라 실패·취소·재시작·cleanup 검증이 통과한 뒤에만 공개한다.
- x86_64와 동적 resize는 별도 capability로 유지하며 arm64 안정 경로를 회귀시키지 않는다.
- Play Asset Delivery를 사용해도 PRoot/loader는 base APK의 JNI 경계를 유지한다.
- SDK는 부팅·process death 이후 사용자 요청 없이 runtime이나 이전 command를 자동 재실행하지 않는다.
- 기존 프로젝트 API, 공식 SDK와 표준 도구를 우선하고 새 의존성은 범위상 필요할 때만 추가한다.

## 잔여 차단 항목 상세와 처리 기준

### 배포 범위 선결정

공개 배포는 자동으로 진행하는 기본 목표가 아니다. Phase 8은 SDK·앱을 제3자에게 배포할 경우를
대비한 readiness gate이며, 실제 배포 범위는 사용자와 저장소 owner가 다음 중 하나로 먼저 결정한다.

| 배포 모드 | 정의 | 현재 판단 |
|---|---|---|
| 내부 전용 | 동일 조직 내부에서만 개발·실행하고 제3자에게 binary를 제공하지 않음 | arm64 내부 개발·sideload 가능 |
| 제한 테스트 배포 | 외부 테스터, 고객, 별도 법인 또는 Play test track에 binary 제공 | 배포·라이선스 의무 검토 필요 |
| 공개 배포 | GitHub Release, 공개 Maven, Play production 등 불특정 제3자에게 제공 | 현재 `No-Go` |

배포 범위가 확정되기 전까지 readiness는 가장 엄격한 **공개 배포 시나리오**를 기준으로
fail-closed 상태를 유지한다. 공개 배포가 목적이 아니라면 Phase 8 gate의 적용 범위와 release manifest를
내부 배포 정책에 맞게 별도 조정해야 하며, 임의로 `READY` 처리하지 않는다.

### 공개 배포 차단 7개

## Q&A 결정 기록

### Q1. 왜 공개 배포를 전제로 했는가? 소스 공개 범위가 있는가?

- Phase 8의 공개 배포 gate는 **배포를 반드시 수행한다는 결정이 아니라**, GitHub/Maven/Play에
  제3자 배포할 가능성에 대비한 최악 조건 readiness 점검이다.
- 동일 조직 내부에서만 사용하고 binary를 제3자에게 전달하지 않는 경우와, 외부 테스터·고객·Play에
  binary를 제공하는 경우의 의무는 다르므로 배포 범위를 먼저 확정해야 한다.
- 이전 lock/SBOM은 PRoot를 `GPL-2.0-only`로 기록했지만, 실제 고정 커밋
  `OpenMinis/proot@8cf13e9`의 소스 헤더는 `GPL version 2 or any later version`이다.
  현재는 source 선언을 `GPL-2.0-or-later`, combined binary 결론을 `NOASSERTION/REVIEW_REQUIRED`로
  분리하고 정합성 검사를 추가했다. 정적 링크된 talloc은
  `LGPL-3.0-or-later`로 기록되어 있으므로 binary를 제3자에게 배포할 경우 해당 구성요소의 정확한
  source, 적용 patch, 재빌드·재링크 자료 제공 범위를 검토해야 한다.
- 배포되는 Alpine rootfs도 하나의 단일 라이선스가 아니라 포함 package별 라이선스를 가지므로,
  GPL/LGPL package의 source 제공·고지 범위를 package manifest 기준으로 추가 감사해야 한다.
- Android 앱 전체 소스를 반드시 공개해야 하는지는 단순히 같은 APK에 들어 있다는 사실만으로 확정할
  수 없다. PRoot가 독립 실행 파일인지, 앱과 하나의 결합 저작물인지, 통신 경계와 링크 방식이 어떤지에
  따라 달라질 수 있으므로 배포 전에 OSS 전문 법률 검토가 필요하다.
- 소스 공개 범위를 확정하기 전까지 공개 배포 gate는 계속 `BLOCKED`로 유지한다.

### Q2. GPLv3 프로그램과 통신하면 연결 프로그램도 모두 GPL 공개 대상인가?

- 아니다. GPLv3은 GPL 프로그램과 통신한다는 이유만으로 모든 상대 프로그램에 자동 적용되지 않는다.
- 판단 기준은 process·socket·pipe 사용 여부 하나가 아니라, 두 프로그램이 법적으로 하나의 결합 저작물인지
  또는 독립 프로그램의 집합인지다. 일반적인 command line, pipe, socket, HTTP 같은 경계는 독립성에
  유리하지만, 복잡한 내부 자료구조와 긴밀한 제어 흐름을 공유하면 결합 저작물 판단 가능성이 커진다.
- 현재 Android 앱은 PRoot를 정적/동적 라이브러리로 링크하지 않고 별도 process로 실행하며,
  argument, environment, PTY/fd와 파일로 제어한다. 이는 독립 프로그램이라는 근거가 되지만 같은 APK에
  필수 runtime으로 내장되고 전용 제어 경로를 사용하므로 배포 전 법률 검토 없이 확정하지 않는다.
- process 경계와 별개로 OpenMinis의 GPLv3 Android/Python 소스 코드를 복사·수정한 부분이 있다면 그
  코드의 파생 저작물 여부를 별도로 감사해야 한다. 아이디어·공개 protocol만 참고한 경우와 실제 구현
  코드를 가져온 경우는 판단이 다르다.
- talloc은 PRoot에 정적 링크되어 있으므로 PRoot와 talloc 사이에는 별도 process 통신 논리가 적용되지
  않는다. 해당 combined binary는 LGPLv3 재링크·source 조건과 PRoot의 GPL v2-or-later 조건을 함께
  충족해야 한다.
- GPLv3과 AGPLv3을 구분한다. GPLv3은 단순 네트워크 사용만으로 source 제공 의무가 발생하지 않으며,
  AGPLv3은 네트워크 사용자에게 AGPL-covered program의 source 접근을 제공하는 추가 조건을 가진다.
  AGPL도 독립 client 전체를 자동으로 AGPL로 바꾼다는 의미는 아니다.

### Q3. clean 구현 앱과 공개 대상 runtime을 어떻게 분리할 것인가?

- OpenMinis의 아이디어·동작·공개 protocol만 참고하고 실제 GPL 구현 코드를 복사하지 않은 clean 구현이며,
  Android 앱이 PRoot/talloc에 링크되지 않고 별도 process/protocol 경계를 유지하면 앱 자체 코드를 GPL로
  공개하지 않는 구조를 목표로 할 수 있다. 단, 모듈 분리는 증거를 강화할 뿐 법적 판단을 자동 확정하지 않는다.
- proprietary 가능 영역은 `alpine-runtime-api`, clean Android host/launcher, HostBridge, Provider/OAuth,
  Python Gateway, chat routing, workspace와 UI다. 각 영역에 GPL 코드가 복사·링크되지 않았다는 provenance를
  파일 단위로 남긴다.
- 공개·제공 대상은 고정 PRoot source, PRoot 수정 patch, loader source/build script, 정적 링크된 talloc
  source와 재빌드·재링크 자료, 해당 license/notice다.
- Alpine rootfs는 package별 라이선스 manifest를 만들고 GPL/LGPL package의 exact source 또는 수령자가
  동등하게 접근 가능한 source 제공 경로를 release version과 고정한다.
- binary 배포 구조는 app artifact와 `oss-sources` bundle을 분리하되 같은 release manifest와 checksum으로
  연결한다. 앱 EULA는 PRoot/talloc/Alpine에 보장된 수정·재배포 권리를 제한하지 않도록 예외를 둔다.
- 현재 모듈 기준으로 `alpine-runtime-pack-bundled`와 `alpine-runtime-pack-x86_64`을 copyleft artifact
  경계로 유지하고, 앱·SDK core가 이 binary를 링크하지 않고 process 실행만 하도록 boundary test를 유지한다.

### Q4. 상세 검토 후 어떤 개발 계획으로 분리했는가?

- 현재 코드 기준으로 PRoot는 Android/JNI에 링크되지 않고 `ProcessBuilder`로 별도 실행되며,
  앱 JNI는 프로젝트 고유 `alpine-runtime-pty`만 로드한다. 이 경계를 유지·검증하는 방향이 적절하다.
- 반면 talloc은 PRoot에 정적 링크되고, PRoot source header와 lock/SBOM/notice 사이의 SPDX 불일치가 있어
  license metadata 정정과 combined binary 검토가 우선 필요하다.
- arm64/x86_64 rootfs package inventory와 native PRoot/talloc source-to-binary archive는 구현됐다.
  다만 6개 Alpine package source origin의 exact source/APKBUILD/patch mirror는 미완료다.
- OpenMinis는 reference-only clean 구현이라는 전제를 파일 단위 provenance 감사로 증명해야 하며,
  감사 전에는 코드 복사 없음이나 앱 비공개 가능성을 최종 승인으로 기록하지 않는다.
- 상세 구현은 [별도 라이선스·대응 소스 개발 계획](implement_20260802_183317.md)으로 분리했다.
  배포 mode/owner 결정 → provenance → metadata 정정 → PRoot/talloc source bundle → Alpine package source
  → module/artifact 경계 → EULA/고지 → 원격 CI 순서로 진행한다.
- 위 계획의 외부 배포 완료 기준을 모두 충족하기 전까지 공개 배포는 계속 `No-Go`다.
