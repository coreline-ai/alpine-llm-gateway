# implement_20260731_233326.md

작성 일시: `2026-07-31 23:33:26 KST`

이 문서는 `새 대화`가 기존 대화를 삭제하지 않고 별도 대화로 생성되며, 사용자가 대화 목록에서 이전 대화로 돌아갈 수 있게 하는 개발 범위를 고정하기 위한 작업 문서다.

## 개발 목적

현재 단일 `ChatUiState.messages`와 `clearConversation()` 중심 구조를 대화 ID 기반 멀티 대화 구조로 전환한다. `새 대화`는 확인 팝업 없이 즉시 빈 대화를 만들되 기존 대화, 입력 초안, 선택 Provider·모델과 응답 상태를 보존한다. 사용자는 대화 목록에서 이전 대화를 다시 열 수 있고, 생성 중인 대화도 목록에서 상태를 확인하고 복귀할 수 있어야 한다.

## 개발 범위

- 대화 ID 기반 `ChatConversation`/`ConversationSummary` 모델을 추가한다.
- 각 대화에 다음 상태를 분리해 보존한다.
  - 메시지 목록과 자동 생성 제목
  - 선택 Provider profile ID와 선택 모델
  - 작성 중인 입력 초안
  - 생성 중·완료·중단·실패 상태와 최근 수정 시각
- `새 대화`는 팝업 없이 신규 대화를 만들고 이전 대화를 삭제하지 않는다.
- 대화 목록 UI에서 이전 대화를 선택해 메시지·초안·Provider·모델 상태를 복원한다.
- 첫 사용자 메시지를 공백 정규화·길이 제한하여 로컬에서 대화 제목을 만든다.
- 대화 이름 변경과 삭제를 제공하며 삭제에만 확인 팝업을 사용한다.
- 앱 재시작 후에도 대화 목록과 메시지를 복원한다.
- OAuth token과 분리된 별도 Android Keystore AES-GCM 키로 대화 payload를 암호화한다.
- app-private conversation 파일을 `AtomicFile`로 저장하고, 한 대화의 손상이 전체 목록 손실로 번지지 않게 한다.
- 대화별 streaming job을 분리하고 최대 동시 생성 수를 2개로 제한한다.
- 사용자가 생성 중인 대화를 떠나도 해당 응답은 백그라운드에서 계속되며 목록에 `생성 중` 상태를 표시한다.
- 각 대화에서 해당 대화의 생성만 `Stop`할 수 있게 한다.
- 프로세스 종료로 중단된 `STREAMING` 메시지는 다음 시작 시 `CANCELLED` 상태로 정상화한다.
- JVM/Compose instrumentation 테스트, 문서, lint, APK 빌드와 삼성폰 수동 smoke test를 갱신한다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 요구사항이 불명확하면 가능한 케이스를 나누고 확인 후 진행한다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고, 각 단위의 역할과 경계를 계획에 적는다.
- 계획 밖 옵션/확장/부가 기능을 만들기 위한 분리는 하지 않는다.
- 공통화는 계획 범위 안의 중복을 줄일 때만 수행하고 과도한 추상화는 피한다.
- 기존 프로젝트 API, Android 표준 API와 현재 JSON codec 패턴을 우선 사용하며 새 의존성은 범위상 필요할 때만 추가한다.
- 대화 내용, 초안과 Provider 응답 원문을 로그·crash message·test tag에 포함하지 않는다.
- OAuth credential 저장소·키 alias와 대화 저장소·키 alias를 분리한다.
- 대화 전환 후에도 진행 중 응답은 시작 당시 Provider·모델 metadata를 유지한다.
- 저장 실패가 streaming UI thread를 막지 않게 파일 IO는 background dispatcher에서 수행한다.

## Phase 4. 대화별 백그라운드 streaming

### 목표

- 사용자가 생성 중 대화를 떠나도 해당 응답을 계속 받고, 다른 대화와 job·오류·중단 상태가 섞이지 않게 한다.

### 구현 태스크

- [x] 단일 `streamJob`을 conversation ID별 active job registry로 교체한다.
- [x] 각 stream이 시작 당시 conversation/provider/model/message ID를 고정 캡처하게 한다.
- [x] active가 아닌 대화의 delta도 해당 대화 저장소와 summary 상태에만 반영한다.
- [x] 전체 최대 2개, 대화당 최대 1개 streaming 제한을 적용한다.
- [x] 세 번째 요청과 같은 overload를 Provider 호출 전에 차단하고 닫힌 사용자 오류로 표시한다.
- [x] 대화 목록의 생성 중·완료·실패 badge와 unread 완료 상태를 갱신한다.
- [x] active 대화의 `Stop`이 다른 대화 job을 취소하지 않도록 한다.
- [x] stream delta 저장은 bounded debounce로 write amplification을 줄이고 terminal event에서 즉시 flush한다.
- [x] retry target과 failure recovery를 conversation ID별로 분리한다.

### 자체 테스트

- [x] A 생성 중 B로 전환·전송 후 두 응답 metadata와 delta가 격리된다.
- [x] background 대화 완료 후 목록 badge와 재진입 내용이 일치한다.
- [x] A의 Stop이 B를 중단하지 않고 B의 failure/retry가 A에 나타나지 않는다.
- [x] 동시 생성 2개 허용과 세 번째 차단 경계 테스트가 통과한다.
- [x] 새 대화·삭제·process clear와 stream completion 경합에서 stale update가 발생하지 않는다.
- [x] delta burst에서도 저장 횟수가 제한되고 마지막 text가 유실되지 않는다.

## 잔여 리스크 / 후속 과제

- Provider가 계정당 동시 요청을 제한하면 앱의 최대 2개보다 더 낮은 실제 제한이 적용될 수 있다.
- 긴 대화가 계속 누적될 때 context window truncation·요약 정책은 별도 계획이 필요하다.
- 대화 파일은 `noBackupFilesDir`로 자동 백업에서 제외했으므로 앱 데이터 이전·Keystore key invalidation 시 로컬 기록은 복구할 수 없으며, 향후에는 안전한 초기화 UX를 보강할 수 있다.
- 대화 검색·고정·클라우드 동기화·내보내기는 이번 계획 완료 후 별도 workstream으로 다룬다.
