## 문서 기반 제약 사항

- OAuth token, authorization code, PKCE state/verifier, callback query, Authorization header,
  Provider raw body, prompt, account 식별자는 source·log·test fixture·계획 문서에 기록하지 않는다.
- 모델 후보는 계정·region·tier·preview lifecycle의 지원 증거가 아니다.
- Gemini의 프로젝트 승인 후보 외 non-Gemini 모델은 기본적으로 `USER_ADDED` 또는 legacy migration으로만
  취급한다. debug compatibility 후보는 release product catalog로 승격하지 않는다.
- profile/model 변경은 OAuth identity 변경이 아니므로 token 삭제나 재로그인을 유발하지 않는다.
- 모델을 비활성화해도 저장된 대화의 `selectedModel`을 자동으로 바꾸지 않는다.
- 사용자가 새 모델을 명시적으로 선택하기 전에는 Send·Retry·fallback dispatch를 모두 차단한다.
- 이미 시작된 stream은 시작 시점의 `(profileId, modelId)` snapshot을 사용하며 catalog 변경으로
  다른 model에 재전송하지 않는다.
- production source와 debug compatibility source를 별도 scanner mode로 검증한다.
- 실제 기기 명령은 Samsung `R3CY40PXCAP`을 명시하며 다른 기기는 사용하지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 계획의 `이슈 및 수정`에 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고, 계획 밖 확장을 위한 추상화는 만들지 않는다.
- 기존 `ProviderProfileStore`, `ChatBackendDescriptor`, `ChatViewModel`, `DirectChatHostController` 계약을
  우선 확장하고 새 저장소·routing 계층·network dependency를 추가하지 않는다.
- migration은 이전 JSON을 읽을 수 있어야 하며 downgrade를 가장해 필드를 삭제하거나 profile을 초기화하지 않는다.
- 실패한 migration/profile validation은 token store와 기존 저장 데이터를 변경하지 않아야 한다.
- 실제 계정·기기·스토어·법무 조건이 필요한 Phase는 진입 조건이 충족됐다는 증거 없이 시작하지 않는다.
- Git 작업은 topic branch에서 진행하고 `reset --hard`, `clean -fd`, 앱 데이터 삭제를 사용하지 않는다.

## 잔여 리스크 / 후속 과제

- debug compatibility 성공은 Provider 공식 모바일 OAuth 지원 또는 출시 권한의 증명이 아니다.
- model ID 후보는 entitlement 증명이 아니며 실제 사용 가능 여부는 Phase 7의 계정별 E2E가 결정한다.
- PRoot guest `SIGWINCH` 원인이 해결되기 전 dynamic resize/full-screen TUI를 지원한다고 표시하지 않는다.
- 문서 evidence 갱신 commit도 current-head CI 검증 대상이므로 마지막 CI 상태는 항상 실제 최종 SHA로 재확인한다.
- 법무·Provider·Play·기기 승인 없이 release gate를 `READY`로 변경하지 않는다.
